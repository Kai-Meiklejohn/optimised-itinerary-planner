# Deploy on AWS

This guide describes a new deployment in your own AWS account. It does not restore the retired service. First complete the [local setup](../README.md#set-up-your-own-copy) and confirm that sign-in, saved trips and maps work with your resources.

The frontend will use **CloudFront → private S3** for files and call **API Gateway → Lambda → DynamoDB** for saved data. Cognito supplies authentication tokens, and Amazon Location supplies maps, places and optional travel estimates. No ALB is required for this setup.

The Terraform module in `infra/` creates the shared application resources only. The hosting steps below use the AWS console and CLI. CI checks the code but does not publish it. These instructions must be verified in your own account before you accept real users or data.

## 1. Prepare an execution role and backend bundle

1. In IAM, create a role with **AWS service → Lambda** as its trusted entity. Name it `itinerary-planner-lambda` or choose your own name.
2. Attach the application policy identified by `terraform -chdir=infra output -raw local_backend_policy_arn`.
3. Attach AWS's managed `AWSLambdaBasicExecutionRole` policy to allow CloudWatch logging. The provisioning identity needs permission to pass this role to Lambda. Do not give the function administrator permissions.
4. From the repository root, build and package the backend. Install the `zip` utility if your terminal does not have it.

```bash
npm ci --prefix backend
npm run typecheck --prefix backend
npm test --prefix backend
npm run build --prefix backend
zip -j backend/backend.zip backend/dist/index.cjs
```

The archive must contain `index.cjs` at its root. Keep this generated ZIP out of Git.

## 2. Create the Lambda function

In Lambda, create a function from scratch using **Node.js 22.x**, the **x86_64** architecture and the execution role from step 1. Choose a name such as `itinerary-planner-backend`.

Upload `backend/backend.zip` as the function code. Set the handler to **`index.handler`**, memory to **256 MB** and timeout to **30 seconds**. Leave VPC attachment disabled for this setup. The function accesses AWS service endpoints without a customer VPC or NAT gateway.

Add these environment variables from your Terraform outputs.

| Lambda variable | Terraform output |
| --- | --- |
| `USER_TABLE_NAME` | `users_table_name` |
| `TRIP_TABLE_NAME` | `trips_table_name` |
| `STOP_TABLE_NAME` | `stops_table_name` |
| `RATE_LIMIT_TABLE_NAME` | `rate_limit_table_name` |
| `COGNITO_USER_POOL_ID` | `cognito_user_pool_id` |
| `COGNITO_CLIENT_ID` | `cognito_client_id` |

Lambda supplies `AWS_REGION` itself. Do not add `AWS_PROFILE`, access keys or a local `.env` file. Add `FRONTEND_ORIGIN` after creating CloudFront in step 3, using its exact HTTPS origin without a trailing slash.

In CloudWatch Logs, set an appropriate retention period for the function's log group, such as 14 days. If the group does not exist yet, it will be created when the function first logs, or you can create `/aws/lambda/YOUR_FUNCTION_NAME` beforehand.

## 3. Create the HTTPS frontend host

1. Create an S3 general-purpose bucket with a globally unique name. Keep **Block all public access enabled**, ACLs disabled and default encryption enabled. Do not enable S3 website hosting.
2. Create a CloudFront distribution whose origin is that S3 bucket's regular endpoint. Select **Origin access control (OAC)** and configure it to sign origin requests.
3. Apply the bucket policy generated by CloudFront. It must allow the CloudFront service to read objects only for this distribution, using the distribution ARN as the `AWS:SourceArn` condition. Do not make the bucket publicly readable.
4. Set the default root object to **`index.html`** and viewer protocol policy to **Redirect HTTP to HTTPS**. Use the default CloudFront certificate and domain, so you do not need a custom domain or certificate for this guide.
5. Use the managed **CachingDisabled** cache policy initially, and the managed **SecurityHeadersPolicy** response headers policy. You can configure caching later once the deployment works. Disabling caching initially avoids stale HTML or worker files during setup.
6. Wait until the distribution is deployed, then record its HTTPS address. Before you upload the frontend, an access-denied page is expected because `index.html` does not exist yet.

Set Lambda's `FRONTEND_ORIGIN` to that HTTPS address, without a trailing slash. Keep a record of the bucket name and distribution ID for uploads.

AWS documents the OAC setup and required bucket policy in [Restrict access to an Amazon S3 origin](https://docs.aws.amazon.com/AmazonCloudFront/latest/DeveloperGuide/private-content-restricting-access-to-s3.html).

## 4. Create an authenticated HTTP API

In API Gateway, create an **HTTP API**, not a REST API. Add your Lambda function as an integration using **payload format version 2.0**. Use the **`$default` stage** with automatic deployment enabled, so the API URL has no stage prefix.

Create a JWT authoriser with these settings.

| Setting | Value |
| --- | --- |
| Identity source | `$request.header.Authorization` |
| Issuer | `https://cognito-idp.YOUR_REGION.amazonaws.com/YOUR_USER_POOL_ID` |
| Audience | Your Terraform `cognito_client_id` output |

Attach the authoriser to the **`$default` route**, with your Lambda integration. Leave authorisation scopes empty because this application sends Cognito ID tokens. Do not add unauthenticated trip, stop or user routes.

Add two explicit routes using the same Lambda integration.

| Route | Authorisation | Purpose |
| --- | --- | --- |
| `OPTIONS /{proxy+}` | None | Allow browser preflight requests |
| `GET /health` | None | Return an empty 200 response for a basic health check |

The console normally adds Lambda invocation permission when creating the integration. Check the function's resource-based policy and ensure the API can invoke it, scoped to your API's execution ARN. Do not enable an unauthenticated Lambda function URL.

Configure API-level CORS as follows.

- Allowed origin is the exact CloudFront HTTPS origin, without a trailing slash. Add `http://localhost:5173` only if you want your local frontend to use this hosted API.
- Allowed methods are `GET`, `POST`, `PATCH`, `DELETE` and `OPTIONS`.
- Allowed headers are `Authorization` and `Content-Type`.
- Leave credentialed cookies disabled. Authentication uses the bearer token header.

API Gateway supplies CORS response headers for this HTTP API. The unauthenticated OPTIONS route matters because an authorised `$default` route would otherwise also capture preflight requests. See AWS's [JWT authoriser](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-jwt-authorizer.html) and [HTTP API CORS](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-cors.html) guides.

Record the API's HTTPS invoke URL. **Use that URL directly for both frontend API variables. Do not add `/api` or `/prod` with this configuration.** The application will append paths such as `/trips` and `/users`.

Before uploading the frontend, check the API from a terminal, substituting your own invoke URL.

```bash
PLANNER_API_URL='https://YOUR_API_ID.execute-api.YOUR_REGION.amazonaws.com'
curl -i "$PLANNER_API_URL/health"
curl -i "$PLANNER_API_URL/trips"
```

The health endpoint should return **200**. The unauthenticated trips request must return **401**. Do not continue if protected data is accessible without authentication.

## 5. Configure keys and build the frontend

Create separate Location browser keys for the hosted site, using the same map/search permissions and optional Routes v2 permission described in the [Location setup](../infra/README.md#maps-and-search). Restrict the allowed referrer to **`https://YOUR_CLOUDFRONT_DOMAIN/*`** and set an expiry. Keep the keys scoped to your resources and required operations.

Copy the frontend template to an ignored production environment file.

```bash
cp .env.example .env.production
```

Fill in every variable in `.env.production` using your own configuration.

| Variable | Hosted value |
| --- | --- |
| `VITE_AWS_REGION` | Region of your Cognito and Location resources |
| `VITE_COGNITO_CLIENT_ID` | Your public Cognito app client ID |
| `VITE_API_BASE_URL` | HTTP API HTTPS invoke URL from step 4 |
| `VITE_BACKEND_API_URL` | The same HTTP API HTTPS invoke URL |
| `VITE_AWS_LOCATION_API_KEY` | Restricted map/search key for the CloudFront origin |
| `VITE_LOCATION_MAP_NAME` | Terraform `location_map_name` output |
| `VITE_LOCATION_PLACE_INDEX_NAME` | Terraform `location_place_index_name` output |
| `VITE_AWS_ROUTES_API_KEY` | Optional separate restricted routing key, or leave blank |

Do not leave either API URL pointing at localhost. `.env.production` overrides `.env.local` during a normal production build, but values exported in your shell take precedence over both files. Remove unintended shell overrides before building.

```bash
npm ci
npm run lint
npm test
npm run build
```

All `VITE_` values are embedded in the public browser bundle. Use only browser-safe configuration here. Rebuild whenever those values change.

## 6. Upload and verify

Use a deployment AWS profile with permission to upload to your bucket and invalidate your distribution. This is separate from Lambda's runtime role. From the repository root, set these variables to your resource names and upload assets before HTML.

```bash
export AWS_PROFILE=your-deployment-profile
PLANNER_BUCKET='your-frontend-bucket'
PLANNER_DISTRIBUTION_ID='your-cloudfront-distribution-id'

aws s3 sync dist/ "s3://$PLANNER_BUCKET/" \
  --exclude 'index.html' \
  --exclude 'assets/maplibre-gl-worker.mjs' \
  --exclude 'assets/maplibre-gl-shared.mjs' \
  --cache-control 'public,max-age=31536000,immutable'

aws s3 cp dist/assets/maplibre-gl-worker.mjs \
  "s3://$PLANNER_BUCKET/assets/maplibre-gl-worker.mjs" \
  --content-type 'text/javascript' --cache-control 'no-cache'
aws s3 cp dist/assets/maplibre-gl-shared.mjs \
  "s3://$PLANNER_BUCKET/assets/maplibre-gl-shared.mjs" \
  --content-type 'text/javascript' --cache-control 'no-cache'
aws s3 cp dist/index.html "s3://$PLANNER_BUCKET/index.html" \
  --content-type 'text/html' --cache-control 'no-cache'

aws cloudfront create-invalidation \
  --distribution-id "$PLANNER_DISTRIBUTION_ID" --paths '/*'
```

Wait for the invalidation to complete in the CloudFront console. Do not add `--delete` to the upload because already-open tabs may still need older hashed assets. The two MapLibre modules keep fixed filenames, so they need their explicit content type and revalidation headers. When changing MapLibre itself, test both a fresh page and an already-open tab.

Open the CloudFront HTTPS URL and check all of the following.

1. Register with a new email, confirm it and sign in. Check password reset too.
2. Create a trip, add a searched place, edit its category and notes, then reload to confirm persistence.
3. Change or remove an activity's address and confirm the map marker follows the saved location.
4. Check maps, search and travel estimates if the routing key is configured.
5. Sign out and confirm saved trips are no longer visible. With a second test account, confirm the first account's trips are not listed.
6. Delete your test trips, check CloudWatch for unexpected errors, and confirm the unauthenticated `/trips` request still returns 401.

The automated tests use mocked AWS services. Passing them does not confirm your account's IAM permissions, email delivery, API authoriser or Location key restrictions. These live checks are required for a new deployment.

## Updates, operations and removal

For backend changes, rebuild the ZIP, upload it to the same Lambda function and wait for the update to finish before publishing a frontend that depends on it. Review any Terraform resource changes separately. The public repository intentionally has no automatic AWS deployment credentials or workflow.

Before accepting real users, configure suitable API throttling, Lambda error/throttle alarms, billing alerts and DynamoDB backups. Decide on Cognito email delivery limits, account abuse controls and your privacy/data-retention policy. Set Location key expiry reminders and test replacements before old keys expire. Budget alerts do not stop spending.

To remove the hosted copy, disable and delete CloudFront before deleting its origin bucket. Delete the HTTP API, Lambda function and associated log group, then detach policies and remove the execution role. Remove separately created Location keys. Finally review and run the Terraform destroy procedure in the [AWS setup guide](../infra/README.md#clean-up). This deletes user accounts and itinerary data, so export anything you need first.
